# Backend — инструкции для агентов

## Контекст

Это серверная часть учебного менеджера задач.

- Технология: Java 21 и Spring Boot 4.1.1
- Репозиторий — монорепозиторий: фронтенд находится в `../frontend`, документация — в `../docs`.
- Приложение состоит из веб-клиента и серверного REST API; консольный интерфейс не является основной точкой взаимодействия.

## Стартовые зависимости

- Spring Web — REST API и Spring MVC.
- jOOQ Access Layer — типобезопасные SQL-запросы к базе данных.
- PostgreSQL Driver — подключение к PostgreSQL.
- Liquibase Migration — версионирование и применение миграций схемы базы данных.
- Validation — проверка входных DTO через Bean Validation.
- Lombok — сокращение шаблонного кода.
- Новые зависимости и плагины не добавлять без предварительного согласования.

### Правила Lombok

- Использовать Lombok только для шаблонного кода: например, `@Getter` и `@RequiredArgsConstructor`.
- Для внедрения зависимостей предпочитать конструктор, созданный `@RequiredArgsConstructor`, а не field injection.
- Не использовать `@Data` без необходимости: оно неявно создаёт `equals`, `hashCode` и `toString`, что может дать неожиданное поведение.
- Для простых неизменяемых request/response DTO предпочитать Java `record`, если это не противоречит задаче.

## Архитектурные решения

- Бэкенд — модульный монолит с REST API в JSON для фронтенда.
- Разделять HTTP-слой, прикладную логику и доступ к данным: `controller` → `service` → `repository`.
- Для доступа к PostgreSQL использовать jOOQ и `DSLContext`; JPA и Hibernate не использовать.
- Классы доступа к данным должны содержать SQL-запросы jOOQ, а сервисы — бизнес-логику и транзакционные границы.
- Не возвращать модели хранения данных из контроллеров; использовать request/response DTO.
- Валидацию входных данных выполнять на границе API через Bean Validation.
- Бизнес-правила и работу с зависимостями задач размещать в сервисах, а не в контроллерах.
- Изменяющие данные операции выполнять в транзакциях; границы транзакций задавать в сервисном слое.
- Ошибки API обрабатывать централизованно через `@RestControllerAdvice`.
- API-контракт согласовывать до реализации экранов фронтенда; изменения контрактов фиксировать в `../docs`.
- Бэкенд не должен зависеть от кода фронтенда.
- База данных — PostgreSQL. Структуру базы данных изменять только миграциями Liquibase.
- Формат дат, идентификаторы и механизм аутентификации пока не выбраны. Не добавлять их без отдельного согласования.

## Данные и бизнес-правила

- Модель задачи включает идентификатор, название, приоритет, статус и дедлайн.
- Статус задачи и приоритет представлять ограниченными значениями, а не произвольными строками.
- Дедлайн валидировать как корректную дату; правило о допустимости прошедших дат определить отдельно.
- Если задача A зависит от задачи B, задачу A нельзя отмечать выполненной, пока не выполнена задача B.
- Перед добавлением зависимости проверять существование обеих задач, отсутствие дублирующей связи и отсутствие цикла.
- Граф зависимостей должен уметь обнаруживать циклы.
- Нельзя удалять задачу, пока не определено, что делать с зависимостями на неё: запрещать удаление, удалять связи или выбирать другой вариант. Не принимать это решение молча.
- Поиск по названию должен явно определять регистр и тип совпадения: полное или частичное. Не выбирать это поведение без согласования.

## Алгоритмы и измерения

- Алгоритмы линейного и бинарного поиска, быстрой сортировки, сортировки вставками, сортировки слиянием, DFS и BST реализовывать самостоятельно.
- Не подменять требуемый алгоритм готовой сортировкой, поиском или структурой данных стандартной библиотеки.
- Бинарный поиск запускать только по данным, отсортированным в соответствии с его предусловием.
- Сортировка для демонстрации алгоритма не должна незаметно менять основное хранилище задач, если пользователь этого не запросил.
- Приоритеты и дедлайны должны иметь чёткое правило сравнения, одинаковое во всех сортировках, BST и рекомендованном порядке выполнения.
- Для каждой реализации сохранять возможность тестирования и замера производительности.
- Замеры алгоритмов отделять от HTTP, базы данных, чтения файлов и логирования — иначе измеряется инфраструктура, а не алгоритм.
- Для каждого размера входных данных выполнять несколько запусков и сохранять методику измерения для отчёта.

## Импорт и экспорт

- Импорт CSV и JSON выполнять через API.
- Каждая импортируемая запись должна проходить ту же валидацию, что и задача, созданная вручную.

## Работа с базой данных

- Миграции Liquibase должны быть последовательными и воспроизводимыми на пустой базе данных.
- Не изменять уже применённую миграцию: для изменения схемы создавать новую миграцию.
- Не смешивать изменения схемы базы данных и несвязанные изменения прикладного кода в одной миграции.

## Правила реализации и совместной работы

- Не добавлять зависимости и плагины без предварительного согласования.
- Менять только файлы, относящиеся к задаче.
- Не перерабатывать существующую структуру без необходимости.
- Одна ветка — одна задача; не смешивать в ней функциональность, форматирование и рефакторинг.
- Перед началом задачи изучить актуальный `main` и существующие изменения в затрагиваемом модуле.
- Не редактировать файлы, принадлежащие другой активной задаче, без согласования.
- При изменении поведения добавлять или обновлять тесты.
- Перед завершением запускать относящиеся к изменениям тесты; если это невозможно, явно указывать причину.
- В описании изменений кратко указывать: что сделано, как проверить и какие ограничения остались.
- Если для реализации не хватает продуктового решения, остановиться и запросить его, а не выбирать поведение самостоятельно.
- Не создавать коммиты и не отправлять изменения в удалённый репозиторий без прямой просьбы.
- Не размещать секреты, токены, пароли и локальные конфигурации в Git.
